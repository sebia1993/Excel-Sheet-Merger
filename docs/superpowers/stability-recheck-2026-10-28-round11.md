# Excel Sheet Merger — 11차 안정성 재감사

기준: v1.3.26 / `0cc28849e5da547ff5bb68a2a00ff4f9e857c568`. 범위: 정상 기능·UI 유지, 실패 경로 자원 수명 관리. 장시간 시험은 최종 단계로 유보.

## 실제 재현한 문제

1. 정상 CSV 다음에 빈 CSV를 넣으면 병합은 실패하고 결과 폴더의 작업 폴더는 정리되지만, OS TEMP에는 openpyxl XML 두 개가 남았다. 라이브러리 Workbook.close()는 이 파일을 지우지 않는다.
2. 손상된 workbook.xml을 읽다 실패하면 예외 객체/traceback이 살아 있는 동안 원본 ZIP의 OS 핸들이 열려 있었다.
3. 정상 모드 또는 스트리밍 모드의 ZIP 저장에 ENOSPC를 주입하면 시트 XML 및 출력 ZIP 핸들의 정리가 성공 경로에 의존했다.

## 반영 내용

- 입력 원본 스트림을 명시적으로 소유하여 파싱 성공/실패 모두 즉시 닫는다.
- openpyxl 3.1.5와 동일한 XML/manifest/drawing 직렬화 절차에 finally 정리를 추가한 전용 저장 어댑터를 사용한다.
- 현재 병합의 Workbook/WorksheetWriter만 정리한다. 전역 TEMP 탐색이나 다른 작업의 파일 삭제는 하지 않는다.
- 저장 실패 후에는 ZIP을 닫고, 정리 오류는 최초 데이터/디스크 오류를 덮지 않도록 처리한다.
- 분류·파일 지문·한국어 UI·원본 보호·번호 부여·압축 안전 한도는 변경하지 않았다.

## 검증 근거

- 최초 신규 테스트 9개 중 8개가 기존 코드에서 예상된 자원 잔존 assertion으로 실패했다.
- 수정 후 신규 테스트 11개 통과. lxml 사용/미사용 두 XML 백엔드에서 각각 실행했다.
- 기존 분류 11개, 디스크 부족 5개, ZIP XML 결합 1개, 100회 반복 병합 1개까지 합쳐 로컬 핵심 테스트 29개 통과.
- 정상 저장 어댑터와 기본 openpyxl 저장 결과의 ZIP 항목 순서·내용을 비교했다. 변동하는 수정시각 필드를 제외하고 워크시트·스타일·주석·링크·관계 XML 내용이 같았다.
- 원본 및 이전 결과 바이트 보존, 반복 실패 12회 후 정상 재실행, 다른 live writer 보존을 확인했다.
- 이 컨테이너는 외부 DNS/추가 패키지 설치가 불가하여 전체 GUI 테스트를 로컬 통과했다고 주장하지 않는다. 전체 Windows CI 및 EXE 스모크 결과는 해당 커밋의 Actions 기록으로 확인한다.
- 독립 리뷰 에이전트가 없어 자체 diff/자원 소유권 리뷰를 수행했다.

## 남은 한계와 다음 기준

- 고압축 정상 Excel의 오탐 가능성은 남아 있다. 압축률만으로 정상/비정상을 확정할 수 없으므로 안전 제한을 임의로 해제하지 않았다. 구조별 메모리 예산 검증 없이 단순 완화는 하지 않는다.
- 프로세스 강제 종료에는 finally가 실행되지 않으며, OS/백신/보안 정책이 임시 파일 삭제를 거부하면 정리가 보장되지 않는다. 다른 작업을 훼손할 수 있는 전역 TEMP 정리는 도입하지 않는다.
- 저장 어댑터는 고정된 openpyxl 3.1.5 내부 인터페이스를 사용한다. 버전 업데이트 시 XML 동등성·실패 경로 검증이 필요하다.
- 대형 네트워크 원본의 표본 밖 변경, 복잡한 Excel 객체 호환성, 장시간 GUI 로그 누적은 기존 한계로 유지된다. 해결됐다고 주장하지 않는다.
- 실제 Windows 11·DRM·SMB 환경의 8시간 시험은 아직 실행하지 않았다. 코드 수준 결함을 먼저 다루고 마지막에 수행한다.
